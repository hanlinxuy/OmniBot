## Pinned runtime trace

The device's `workspace/.omnibot/skills/omniflow-gui-runtime` reports runtime `2026.08.21.catalog.dc201798.d453a47e`. Its `core.py`, `execution.py`, and `engine.py` SHA-256 hashes match the corresponding files in the repository's `artifacts/omniflow-gui-runtime-2.1.8.zip`. In that pinned code, `runtime/core.py:execute_action` dispatches one action, observes afterward, and returns a successful `StepResult` whenever `host.act` reports success; it does not compare the before/after observations for ordinary actions. `runtime/execution.py` carries that result through the robust-action path. `runtime/engine.py` sets `previous_action_error` only when the step fails, so a successful `gesture_dispatched` reaches the next model turn without a no-progress error. Android's gesture result itself indicates dispatch, not target effect. This explains the missing signal in this code path, but does not by itself prove every fallback tap in the historical run left the interface unchanged.

A safe fix still needs a validated observation comparator and scope: a keyboard focus, drawing stroke or scroll can be meaningful even when an accessibility tree is unchanged, and a wheel can change while moving away from its target. The next concrete test should replay synthetic before/after observations through the existing runtime action boundary, including an unchanged fallback click, focus-only click, drawing swipe and changed date wheel; then check that any error reaches the existing ModelHost reflection path. Do not introduce a separate lifecycle or automatically repeat a dispatched gesture. The original BA03 requires a dog with two ears and a tail, a local modification preserving other strokes, and export; the unclosed near-circle satisfies none of those acceptance criteria.

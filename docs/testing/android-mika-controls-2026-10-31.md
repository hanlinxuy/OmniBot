# Mika 本地控件适配：2026-10-31 vivo X100 结果

代码与原理见 [研究记录](../research/mika-local-ui-controls.md)。本轮使用现有 vivo X100 开发机；没有换模型，设备 GUI 场景日志仍解析为 `deepseek-flash`。APK 已安装，Python 模块通过官方 override 接口应用。结果只代表这些有界样本，不是稳定性统计或全场景覆盖。

系统闹钟另以正常聊天执行：一次 `alarm_reminder_create(mode=clock_app, skipUi=true)`，结果明确 `creationVerified=false`，随后 GUI 只读核对（4个动作），没有滚轮创建。模型核对后停在列表下方，原 runner 只看当前可见行，未找到上方测试闹钟，原报告保留失败。补充向列表顶部有界滚动后，独立 XML 验证唯一测试标题、07:00、每天、开启；只选择该行并确认单项删除，删除后标记消失、可见初始基线保留。该结果是原生创建成功加补充验收/清理，不是原 runner 一次全通过。

计算器两轮耗时不同同时受模型调用数、API 延迟和额外历史导航影响，不能将 36.411→12.501 s 全部归因于去掉 sleep，也不作为 Mika/OmniBot 对比基准。源码和日志能证明减少模型往返、原生动作以及跳过已完成的重复等待。

日期选择器不显示年份；本轮设备日期为 2026-10-31，目标为6天后。月日、星期、时间、仅一次有独立读回；年份仅由设备日期和连续轨迹支持，没有从持久层独立读出年份。可见基线比对不代表屏幕外数据或云同步的全量审计。

条件等待另做显式工具组件检查：`wait_until(condition=stable, timeout_ms=3000)`，整轮4.471秒、0个变更动作，RunLog 记录条件满足并正常结束，执行后前台仍为时钟。它验证工具接通和只读行为，不是自然任务采样或长时间加载稳定性测试。

## 回归框架变化（与产品修复分开）

- 新增 `li21-todo-reminder`：设备日期起6天后17:00的单次提醒，按唯一标记独立重开、读回、删除；属于 LI21 的有界变体。
- 计算器准备/清理先检查并关闭历史面板，随后 AC 和显示区验收；不清除已有历史。
- 提醒重开、取消、完成等导航增加明确后置条件。仅在系统报告 uncertain 且新观察确认目标页时接受结果，不重放点击。第2次整轮使用补充观察完成验收，后置条件修复不反向改写原报告。

# Contacts provider visibility and uncertain write, 2026-10-30

A normal-chat Android adaptation requested creation and readback of one uniquely marked fictional contact in the local phone account. At baseline the system provider had seven raw contacts; their IDs, account types and deletion flags were retained privately. The app's `contacts_query`, both filtered and unfiltered, returned successful empty results. `contacts_create` then returned `provider_error` with an uncertain write outcome; after another empty app query, the agent attempted creation through the GUI. This cross-channel retry was unsafe because the query was not reliable. A later independent system-provider read found one matching local raw contact with the exact test fields. The evidence does not determine which attempted write created it or rule out a transient duplicate before that read.

The sole matching test raw contact was independently identified by exact name, data and local account, removed by its verified raw ID, and its exact-name query returned no result. The original seven raw-contact IDs, account types and deletion flags matched baseline afterward. This is not a full content comparison of those seven records. No contact names, phone numbers or IDs are published here.

A temporary debug-only count probe in the app process, without emitting names or numbers, established that both aggregate and data-provider queries returned seven rows, but the projected contact IDs and aggregate names were null. The production data query silently skipped null IDs and falsely returned a successful empty list. Permission grants and app-op allow were observed, but the cause of the provider's null fields is not established. The temporary probe source was removed after use and the previous debug result file restored exactly. App-side results and private provider receipts remain under `.session-history/scan-20261030-contact/`.

The narrow product correction reports `provider_data_unavailable` if a returned data row lacks a readable contact ID, rather than calling that row absent. For a filtered empty result it also probes the unfiltered supported-contact data for the observed redaction pattern; a genuinely empty provider still returns an empty result. The generic provider-error message now warns that an uncertain write must not be repeated through any tool or UI without a reliable independent confirmation; this is guidance, not an execution-enforced cross-channel lock. Seventeen focused JVM tests passed, including redacted filtered/unfiltered rows, genuine emptiness, and the uncertain-write message.

On the device, the fixed app-process debug probe returned `provider_data_unavailable` instead of success/zero, and one normal-chat read-only query of the now-absent test marker also surfaced that error without UI fallback or a write. The provider baseline and marker absence were independently rechecked. This verifies the observed null-row failure mode and filtered path; it does not restore access, prove why fields are null, verify contact creation, guarantee behavior when a provider returns zero rows while hiding all data, or establish that all future models will obey the uncertain-write warning.

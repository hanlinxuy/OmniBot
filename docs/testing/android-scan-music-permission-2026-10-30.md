# LI12 album read and notification permission side effect, 2026-10-30

A normal-chat read-only adaptation asked for the visible first three tracks of a public album in an installed music app. Independent post-turn accessibility observation on the NetEase Cloud Music album page confirmed the album name, artist and the three tracks returned by the agent. This passes the bounded page-reading subcase, not LI12's personal collection and release-catalog comparison. The first VLM run failed after 20 actions; a second succeeded after 12. No playback, download or social-action click was identified in those RunLogs, but search history and other incidental app state were not exhaustively audited.

The first RunLog records the agent selecting the system notification permission dialog's “deny and don't ask again” control. Its reasoning treated denial as having no side effects. The final answer then asserted that nothing was changed. Post-run package inspection shows `POST_NOTIFICATIONS` denied with `USER_SET|USER_FIXED` for a reported user entry. The precise pre-run permission and flags were not captured, so the difference from the original setting cannot be established and no restoration was performed. The permission click itself is an observed lasting-setting interaction and the blanket no-change claim is unsupported. The user was asked how to handle the setting; leave it untouched pending their decision. This is a product behavior/communication issue rather than a failure of album text extraction.

During monitoring, an `app_access_state_unknown` guard refused one read. The same request was subsequently read through the existing guard and reached natural `end_turn`; no replay or guard bypass was used. Private run logs and page observation remain under `.session-history/scan-20261030-li12-music/`.

A narrow follow-up exposes a dispatched click on the exact captured system `permission_deny_and_dont_ask_again_button` in the outer VLM result context for successful, failed and cancelled runs. It tells the outer model that a permission decision occurred, and explicitly does not assert the permission's prior or resulting state. This reports the observed action; it does not prevent permission decisions, cover other system controls, or guarantee the model's final wording. The focused JVM test uses the captured action/result shape and passes alongside the existing context payload tests. No actual device permission was reset or toggled for verification; real-device/model behavior with this change remains unverified.

## 第一批：先完成三个可交付项

1. **补齐真实回归闭环。** 用当前原生路径和控件工具跑一次 `li21-todo-reminder` 与系统闹钟。待办已有导航后置条件修复尚未在整轮 runner 中验证；闹钟验收/清理需要有界查找唯一测试标题，不能把当前屏幕看不到视为不存在。新观察确认已到达目标页时接受不确定导航结果，不重新点击。验收仍需独立读回，清理只针对唯一测试对象。产品成功、自动验收通过和辅助恢复分别记录。每个边界最多两次有依据的修复复验，仍阻塞则留证切换。
2. **定位并减少滚轮与批量动作的实际成本。** 按模型调用、原生动作、观察/截图、等待分别记录时间；优先查看 42 个动作的待办运行，识别真实重复观察和等待。只有控件确实提供有效 range/SET_PROGRESS 且数值语义已读回确认时才走直接设值；否则在现有执行所有权内优化原生步进。不得假定 SeekBar 都支持任意设值或都按 24/60 循环。批量动作每步保留新状态定位、已有守卫、取消与日志，不引入第二套执行器或盲重放。选一个明确瓶颈修改，再用同一目标和可比起始状态做小样本前后验证；保留失败，不宣称统计显著或固定倍速。
3. **扩展到两个尚未覆盖的低风险自然任务。** 从场景库选依赖已满足、能独立验收和精确清理的任务，至少涉及一种已改控制能力。优先原生系统接口，其次控件语义，再用视觉补充不可读部分。不要重磨 ZIP，也不要只测显式工具调用。成功路径写入适用的仓库回归用例/开发 skill，说明执行层级与局限；skill 不等于手机自动学会。

若第一项无须产品修改，只修验收器并尽快进入第二、三项。不要为了一个测量数字无限复跑计算器。事件驱动等待、按需截图、跨年或自绘滚轮 OCR 作为后续候选，只有本批证据证明是优先瓶颈才展开，避免一次扩大多条技术路线。

## 验收与交付

- 每个样本记录：唯一测试标记、执行层级、模型调用数、实际动作数、产品耗时、独立验收、清理主体/结果、局部或完整覆盖。系统 Intent 返回成功不是业务结果证明；没有年份字段的选择器不得声称持久年份已验证。
- Python 修改继续走官方 override；应用前比对设备与仓库源码，保留现有 override，读取应用后的内容/哈希。固定运行时 ZIP 不改。APK 只在确认没有在途任务后更新。
- 单项找不到明确根因、依赖不满足或复验仍失败：保存简洁证据并切换任务；完全无可做项时回传主线程，说明具体阻塞，不空转。
- 每完成一批提交并推送 fork，同步 Issue #3；回传主线程提交、实际覆盖、产品修复与框架变化、耗时及未解决项。不要等到所有任务都结束才报告阻塞。
- 第一批三个交付项完成后汇总交接，由主线程审查下一批。旧六小时自动化预算已经结束，本计划不恢复旧自动化，也不继承旧截止时间。

# Android font-size experience scan — 2026-10-30

A natural normal-chat request marked as a test asked to increase system font size by one step while preserving other display settings. Baseline `font_scale` was 1.0 and display density was physical 560 with no override. The persisted ACP turn ended; independent settings read showed `font_scale=1.12` and the same density. Retained GUI snapshots showed the size move from “标准” to adjacent “大”, with font weight “标准” both before and at the final GUI state. The host restored `font_scale=1.0` and read back the original density. This verifies the scoped outcome with host restoration, not the upstream maximum-font-and-icons scenario.

The route was costly and included unintended intermediate changes: three GUI component runs failed with `vlm_planner_failed` and `finish_reason=length` (4, 1 and 2 actions), then a successful run reached maximum font size; the Agent pressed “还原默认” and finally selected the adjacent “大” step. The original snapshots show the weight was already standard, but this reset could have affected a non-default user baseline; the request did not authorize a general reset. A saved state XML was 35,121 bytes, but the observed record does not establish why the model hit its output-length limit, and the Agent's larger XML-size explanation is not independently substantiated. There is no product fix in this batch.

The turn also wrote one daily-memory entry describing the test action and final setting; the host subsequently restored the font, so that entry would be stale. The host located the unique exact entry in the daily memory file, selected one corresponding card in Memory Center, confirmed its text in the delete dialog, and deleted it via the application. A private before/after comparison found the exact entry removed and all other source lines unchanged. Search-index cleanup follows the app's existing deletion path; off-device state was not audited. No broad memory deletion occurred.

The initial host ACP snapshot failed while access state was unknown; only read-only snapshots were retried, including after one SQLite/WAL copy race. The request was not replayed. Raw conversation, screenshots and memory contents remain private and ignored.

## Length-terminated tool-call boundary

The pinned GUI planner constructs model requests with `max_completion_tokens=512`, `reasoning_effort=none`, and `enable_thinking=false`. This records the request configuration; provider enforcement and the exact reason for the three empty `finish_reason=length` responses are not established. Those three recorded responses had no content or tool calls and were rejected by the existing stream accumulator; the Agent then chose additional GUI invocations, not an automatic transport replay of the same logical tool call.

A separate source inspection found that a `length`-terminated model response containing a syntactically complete-looking native tool call could pass through `OmniFlowModelHost.modelTurn` to the runtime parser. The host now rejects `length`, `max_tokens`, and `max_output_tokens` before returning any tool call, without retry. The pinned runtime catches the error as `vlm_planner_failed`, ending that GUI run. A synthetic unit test supplies a valid-looking click with `finish_reason=length` and confirms rejection after one model call; existing normal tool-call tests remain positive. This prevents execution of an untrusted truncated call; it does not increase the budget or resolve the observed empty responses, model rerouting, mistaken maximum setting, or reset behavior.
